All file:line references verified against the working tree (2026-07-02). Review round 1 (30 findings) folded in; see §12 revision log and §13 rejected points.

## 0. Executive summary

- Recurring tasks remain **one `Task` row + inline `recurrenceConfig`**; occurrences are never pre-spawned (preserves ADR 0002 / ADR 0054).
- Editing ONE occurrence **materializes a real `Task` row** (an *override task*) linked to the parent by `(parentTaskId, originalStartAt)` — the iCalendar RECURRENCE-ID pattern, **not** a content hash (§2).
- The override is a first-class task: own id, own reminders, own completion, own delta-sync tombstone. It survives parent rule changes (kept, flagged `detachedAt` when its slot no longer exists) and parent deletion is an app-level cascade soft-delete (§6).
- Expansion stays **server-side** (deviation from the prompt's "iOS expansion change" — the client never expands RRULE, `CalendarStore.swift:517-519`; the suppress-and-merge algorithm lands in `TaskService.findOccurrencesInRange`, and iOS keeps consuming pre-expanded `OccurrenceDTO`s — §5).
- The existing per-occurrence **skip** mechanism (`TaskOccurrenceException`) is kept for skip; per-occurrence **completion** stays exception-based for non-overridden slots but is **redirected to the child** when a live override exists (§7.1, rev). The exception table's `overrideStartAt/overrideEndAt/overrideTitle` capability is deliberately migrated into override tasks (§9).
- **DELETE semantics (rev):** a mode-less `DELETE /tasks/:childId` means *remove the occurrence* (soft-delete child + skip exception on the slot) — every legacy caller (assistant, old iOS builds) gets delete-means-delete. `revert` is an explicit opt-in used only by the new "Revert to series schedule" UI (§4.3).

Why materialized overrides beat the current exception rows for content edits: exceptions are matched by exact epoch-ms `originalStartAt` and get **silently orphaned** whenever the parent's startAt/rule/timezone changes (Landmine A, `task.service.ts:704-710` vs `recurrence-rule.service.ts:564,671-681`). An override task carries its own `startAt`, so the user's edited event keeps existing verbatim after any parent change — only its *link* can go stale, and that is handled explicitly (§6).

## 1. Architecture overview

```
                          ┌───────────────────────────────┐
                          │ task (parent, recurring)      │
                          │  recurrenceConfig JSONB       │
                          │  recurrenceUpdatedAt (NEW)    │
                          │  updatedAt  deletedAt         │
                          └──────────────┬────────────────┘
             suppression by identity     │ 1:N (parentTaskId FK)
        ┌────────────────────────────────┼──────────────────────────┐
        ▼                                ▼                          ▼
 TaskOccurrenceException          task (override child)      task (override child)
 (isSkipped, completedAt for      parentTaskId = parent.id   detachedAt = <ts>
  non-overridden slots)           originalStartAt = R-ID     ("slot no longer
  UNIQUE(taskId, originalStartAt) recurrenceConfig = NULL      generated by rule")
                                  own startAt/endAt/title/
                                  reminders/completedAt
```

Read path (`GET /tasks`, `findOccurrencesInRange`, `task.service.ts:457-496`):
1. Expand the parent's **effective** rule over the window (unchanged engine, `recurrence-rule.service.ts:496-615`; group-inherited anchors included as today, `task.service.ts:1316-1391`).
2. Apply exceptions (skip/completion) as today.
3. **NEW — suppress** every generated instance whose `(parentId, originalStart)` matches a live override child (epoch-ms map, same technique as `indexExceptions`, `recurrence-rule.service.ts:671-681`). The suppression map is built for **both** own-config anchors and group-inherited anchors.
4. **NEW (rev) — one-off wrap suppression for former parents:** when a task that has live attached children is itself wrapped as a one-off (its rule was cleared, `task.service.ts:1250-1303`), its single wrapped occurrence is suppressed if a live child exists with `originalStartAt == task.startAt`. This prevents the duplicate (one-off parent + anchor-slot child) after a recurrence-clear (§8#18).
5. Override children fall out of the ordinary **one-off branch** automatically (tasks with `startAt` in the window, `recurrenceConfig = NULL`) and are merged into the occurrence list, tagged with `parentTaskId`/`isDetached`. The one-off filter `inheritsGroupRecurrence` (`task.service.ts:1239-1241`, applied at :1283) is guarded so a child is NEVER excluded (§3.3.2).

Write path: `POST /tasks/:id/occurrences/override` creates/updates the child (§4.2). Sync: children are ordinary `Task` rows, so `GET /tasks/changes` (`task.controller.ts:119-144`) reports their upserts and soft-delete tombstones with zero delta-endpoint changes (§7.4).

## 2. Occurrence identity: (parentId + originalOccurrenceDate), not content-hash

**Decision: composite key `(parentTaskId uuid, originalStartAt timestamptz)` — the UTC instant the rule generated for this slot, BEFORE any override. Exactly iCalendar RECURRENCE-ID.**

| Criterion | Content-hash | (parentId, originalStartAt) |
|---|---|---|
| Stability under content edits | ✗ any hash including title/notes/time changes when the user edits — identity must survive the very operation it exists for. A hash restricted to (parentId, occurrenceStart) is just an obfuscated, non-invertible composite key with zero benefit | ✓ stable by definition; only parent rule/anchor edits can invalidate it, which is handled explicitly (§6) |
| TZ / DST safety | ✗ hashing local wall-clock collides on DST fall-back (the repeated 01:30 hour) and drifts if tz representation changes | ✓ UTC instant; the engine already generates DST-correct UTC instants from wall-clock in `task.timezone` (`recurrence-rule.service.ts:477-496`); two fall-back instances have distinct UTC epochs |
| Uniqueness | needs salting/collision story | ✓ a rule generates each instant at most once per series; enforced by partial unique index (§3) |
| Compatibility with existing mechanism | ✗ new identity space | ✓ **identical** to the existing `TaskOccurrenceException` unique key `(taskId, originalStartAt)` (`task-occurrence-exception.entity.ts:12`), the wire contract (`PATCH /tasks/:id/completion` + `originalStart` body), and the iOS `occurrenceKey = "seriesId#iso"` (`TaskItem.swift:34,156`) and `OccurrenceVM.id` (`OccurrenceVM.swift:16-23`) |
| Debuggability | opaque | human-readable, queryable |

Compatibility posture: **stay compatible.** The completion/skip exception mechanism keeps its key; overrides use the same key shape; no client identity migration.

Precision rules (existing landmines, made normative):
- Wire: `originalStart` MUST be fractional-seconds ISO. The shared `APIClient` encoder truncates milliseconds, which is why `CalendarStore.isoFractional` exists (`CalendarStore.swift:79-87`) — the new create-override request must serialize `originalStart` as a **string** via `isoFractional`, never a `Date` through the default encoder.
- DB: `timestamptz` compare at epoch-ms exactness, matching `recurrence-rule.service.ts:564`.
- Local SwiftData `occurrenceKey` keeps its whole-second formatter (`TaskItem.swift:149-152`) — acceptable, server anchors are whole-second in practice; do not "fix" this asymmetry in this project.

## 3. Data model (Postgres / TypeORM)

### 3.1 Columns on `task` (no new table — an override IS a task)

New nullable columns on `task` (`src/modules/database/entities/task.entity.ts`):

| Column | Type | Semantics |
|---|---|---|
| `parentTaskId` | `uuid NULL`, FK → `task(id)` **ON DELETE SET NULL** | non-null ⇒ this row is an override child. SET NULL (not CASCADE) as a hard-delete safety net: Task is only ever soft-deleted today, and if a hard delete ever appears (note: `task.calendarId` is `onDelete: 'CASCADE'`, `task.entity.ts:30-35`, so a calendar hard delete DOES hard-delete tasks), degrading children to standalone rows is safer than silent destruction. The *real* delete semantics are app-level cascade soft-delete (§6.2). |
| `originalStartAt` | `timestamptz NULL` | RECURRENCE-ID: the rule-generated UTC instant this override replaces. Immutable after creation. Survives orphaning (see CHECK below, rev). |
| `detachedAt` | `timestamptz NULL` | set when the parent's effective rule no longer generates `originalStartAt` (§6.1); cleared if a later rule edit regenerates it. |
| `recurrenceUpdatedAt` | `timestamptz NULL` **(rev, new)** | bumped ONLY when the task's **effective-rule input set** changes: own `recurrenceConfig` replace/clear, `startAt`, `timezone`, `isAllDay`, `groupId` (when old or new group carries a rule), and by the group-side sweep when the owning group's rule changes or the group is deleted. NOT bumped by completion/skip parent-touches. This is the client's discriminator for "re-expansion needed" (§5.5) — fixes both the over-fire (every completion touch would otherwise wipe all month memos) and the under-fire (group-inherited parents have `recurrence: null` on the wire). |

Why columns on `task` and not a separate override table: the entire point is that the override behaves like a normal task — reminders (`notification_rule.taskId` FK, `1783200000000` migration), soft-delete tombstones, `updatedAt` delta visibility (`IDX_task_calendarId_updatedAt`, migration `1782700000000`), effective-settings/group membership — all come for free only if it lives in `task`.

### 3.2 Indexes / constraints

One migration. **(rev)** Timestamp `1783700000000` is already taken by `1783700000000-seed-persona-presets.ts` (verified in `src/migrations/`); use the next free slot, e.g. `1783800000000-add-override-tasks.ts`.

```sql
ALTER TABLE task
  ADD COLUMN "parentTaskId" uuid NULL REFERENCES task(id) ON DELETE SET NULL,
  ADD COLUMN "originalStartAt" timestamptz NULL,
  ADD COLUMN "detachedAt" timestamptz NULL,
  ADD COLUMN "recurrenceUpdatedAt" timestamptz NULL;

-- one live override per slot; allows re-create after a soft-deleted revert
CREATE UNIQUE INDEX "UQ_task_override_slot"
  ON task ("parentTaskId", "originalStartAt")
  WHERE "parentTaskId" IS NOT NULL AND "deletedAt" IS NULL;

-- child lookups (suppression query, cascade delete, detach sweep)
CREATE INDEX "IDX_task_parentTaskId"
  ON task ("parentTaskId")
  WHERE "parentTaskId" IS NOT NULL;

-- (rev) ONE-DIRECTIONAL: child ⇒ has a RECURRENCE-ID. The reverse direction is
-- deliberately NOT constrained: the FK's ON DELETE SET NULL must be able to
-- orphan a child (parentTaskId NULL, originalStartAt retained) without the
-- referential action itself violating a CHECK and aborting the parent DELETE.
ALTER TABLE task ADD CONSTRAINT "CHK_task_override_pair"
  CHECK ("parentTaskId" IS NULL OR "originalStartAt" IS NOT NULL);
-- app-level invariant additionally enforced in service: parentTaskId ⇒ recurrenceConfig IS NULL
```

(rev, was review issues 3/15/26) The previous bidirectional CHECK `(parentTaskId IS NULL) = (originalStartAt IS NULL)` contradicted the FK's SET NULL: any hard delete of a parent (including a calendar-CASCADE, which hard-deletes tasks) would fire SET NULL on children and trip the CHECK, aborting the DELETE. The one-directional form keeps the invariant that matters (a child always knows which slot it replaces) while making the safety net reachable. An orphaned row (parentTaskId NULL, originalStartAt set) is a legal standalone task; `originalStartAt` on a parentless row is inert residue.

### 3.3 Invariants (service-level guards)

1. `parentTaskId != null` ⇒ `recurrenceConfig` must be `NULL`; `PATCH` attempting to set recurrence on a child ⇒ 400.
2. **A child never inherits group recurrence — enforced at ALL THREE gates (rev, was issue 23):** introduce a single resolver `effectiveRecurrenceConfig(task): RecurrenceConfig | null` that returns `null` whenever `task.parentTaskId != null`, and route through it:
   - the effective-settings resolver (`src/modules/task/effective-settings.ts:31-40`),
   - the group-inherited anchor scan (`task.service.ts:1316-1391`),
   - **`inheritsGroupRecurrence` (`task.service.ts:1239-1241`), used by `readOneOffOccurrences` at `:1283`** — without this third guard, a child inside a group that has `recurrenceConfig` is excluded from the one-off wrap AND from the anchor scan, i.e. it vanishes from every window read, daily-counts, the assistant agenda, and reports while still suppressing its slot.
3. No override-of-override: create-override on a task with `parentTaskId != null` ⇒ 400.
4. `originalStartAt` immutable via PATCH (server strips/rejects).
5. Parent must be **effectively** recurring (own or group-inherited config) at creation time — checked with the effective-config membership helper of §4.2 step 3, not the own-config-only `ensureGeneratedOccurrence`.

### 3.4 `TaskOccurrenceException` after this change

Reduced role: **skip (`isSkipped`) and per-occurrence completion (`completedAt`) for non-overridden slots.** `overrideStartAt/overrideEndAt/overrideTitle` are deliberately migrated to override tasks (§9 backfill) and their write path removed (assistant rewire, §7.3). Columns stay in place for one release (the expansion's `buildOccurrence` at `recurrence-rule.service.ts:448-474` keeps applying them until the backfill has run), then dropped in a follow-up migration. **(rev)** Before the column drop, orphaned legacy override rows that the backfill deliberately did not convert (§9.2c) are archived (JSON dump or log table) so no data is silently destroyed.

## 4. API contracts

### 4.1 DTO changes

`TaskDTO` (`src/modules/task/dtos/task.dto.ts`) — add, all nullable (old clients: Swift `Codable` ignores unknown keys, safe):
- `parentTaskId: string | null`
- `originalStartAt: string | null` (fractional ISO)
- `detachedAt: string | null`
- `recurrenceUpdatedAt: string | null` **(rev)** — client widening discriminator (§5.5)

`OccurrenceDTO` (`task.dto.ts:116-186`, mapper `260-291`) — add:
- `parentTaskId: string | null` — non-null ⇒ this occurrence is a materialized override (its `taskId` is the CHILD's id)
- `isDetached: boolean` (default false)

`ChangesDTO` (`changes.dto.ts:97-109`): **no shape change.** Children ride `tasks[]`/`deleted[]` as ordinary rows (with the new TaskDTO fields).

### 4.2 `POST /tasks/:id/occurrences/override` (new; `:id` = parent)

Body:
```jsonc
{
  "originalStart": "2026-07-10T09:00:00.000Z",   // REQUIRED, fractional ISO, pre-override instant
  // optional patch, tri-state semantics identical to UpdateTaskDto (undefined=inherit-from-parent-snapshot, null=clear):
  "title": "...", "notes": "...", "startAt": "...", "endAt": "...",
  "isAllDay": true, "requiresCompletion": true, "color": "#...", "icon": "...",
  "groupId": "...", "reminders": [{ "offsetMinutes": -30, "channel": "PUSH" }]
}
```

Behavior (`@Transactional`, mirroring the atomicity of f2bea1e):

0. **(rev, was issue 5a) Lock the parent row** — `SELECT ... FOR UPDATE` on the parent task as the first statement. The rule-edit + detach-sweep transaction (§6.1) and the completion-redirect check (§4.5) take the same lock, serializing check-then-insert against edit-then-sweep. Without it, a concurrent rule PATCH can commit a NEW rule + sweep(∅) between this endpoint's membership check and its child insert, committing a permanently mis-attached child.
1. Ownership check (as `task.controller.ts` does today); parent must be **effectively** recurring.
2. If a **live child** already exists for `(parentId, originalStart)` → **upsert semantics**: apply the patch to the existing child, **re-run exception absorption (step 4) on this branch too** (rev, was issue 13 tail — a late-arriving exception written between create and this upsert gets swept up), return `200` with its `TaskDTO`.
3. Else validate membership with a **new effective-config membership helper** (rev, was issue 22): `ensureGeneratedOccurrence` (`task.service.ts:1569-1598`) throws whenever `task.recurrenceConfig` is null and expands only the own config — it would 400 every group-inherited series. Add `ensureGeneratedOccurrenceEffective(task, originalStart)` that resolves `effectiveRecurrenceConfig(task)` (own ?? group, per §3.3.2's resolver) and reuses the same 1ms-bracketed expansion. (Side note for a separate ticket: `POST /tasks/:id/skip` → `applyOccurrenceOverride` shares this own-config-only limitation today; do not fix silently here.)
4. **Absorb any existing exception row** at that key. Base values (rev, was issues 7/29):
   - `startAt = exception.overrideStartAt ?? originalStart`
   - `endAt = exception.overrideEndAt ?? (startAt + parentDuration)` — `overrideEndAt` is independent of `overrideStartAt`; the assistant's move gate exists precisely to preserve a prior length change (verified docblock, `task-occurrence-exception.service.ts` `findOverride` and the dispatcher span warning in the `'this'`-scope edit handler). Dropping it silently reverts resized occurrences.
   - `title = exception.overrideTitle ?? parent.title`, `completedAt = exception.completedAt`
   then **hard-delete the exception** and `touchUpdatedAt(parent)` (`task-database.service.ts:26-28`) — after this, suppression for the slot is carried solely by the override.
5. Create child: `calendarId/groupId/notes/isAllDay/timezone/requiresCompletion/color/icon/notificationStrategyId` snapshotted from parent, `recurrenceConfig = NULL`, `parentTaskId`, `originalStartAt`.
6. **Copy the parent's per-task `NotificationRule` rows to the child** (offsets are start-relative so copy verbatim; note this is precisely what `splitSeries` forgets to do today — `task.service.ts:910-926` — do not repeat that bug).
7. Apply the request patch (reminders array = full-replace semantics as in `task.service.ts:777-781`).
8. `touchUpdatedAt(parent)` — bumps parent into the delta so clients invalidate the affected windows (§7.4). Do NOT bump `recurrenceUpdatedAt` (the rule did not change).
9. Return `201` + child `TaskDTO`.

**Duplicate-create race recovery (rev, was issue 5b):** the previously specified "catch the unique violation, reload, re-apply" cannot run inside the same transaction on Postgres — a 23505 aborts the enclosing tx (25P02) and every subsequent statement fails; typeorm-transactional provides no implicit savepoint. Specify instead: catch 23505 **outside** the transaction boundary (controller/service wrapper) and retry the whole endpoint body exactly once — the retry takes the FOR UPDATE lock, finds the now-committed child, and lands in the upsert branch (step 2), returning the promised idempotent 200.

### 4.3 Child lifecycle = existing task endpoints

- `PATCH /tasks/:childId` — normal update (guards §3.3).
- `PATCH /tasks/:childId/completion` — non-recurring branch, master `completedAt` (`task.service.ts:588-594`); no `occurrenceStart` in body.
- **`DELETE /tasks/:childId?mode=remove|revert` — default is `remove` (rev, was issues 1/12/24, critical).** The child-aware semantics live inside `TaskService.remove` itself (`task.service.ts:940-946`), so EVERY caller inherits them — the REST controller, the assistant's delete tool (`tool-dispatcher.service.ts` `handleDeleteTask`, which calls `taskService.remove(context.userId, target.taskId)` verbatim), and old iOS builds whose `deleteTask` sends a bare mode-less `DELETE /tasks/:id` (`CalendarStore.swift:837-849`, verified: no query param). With the previous `revert` default, every one of those callers would resurrect the occurrence the user just deleted.
  - **`remove` (default, mode absent):** soft-delete the child AND, in the same transaction, upsert `{isSkipped:true}` on the parent at `originalStartAt` — **unconditionally**, even when the child is detached (rev, was issue 8): a skip at a currently-non-generated instant is inert under today's lenient exception semantics and becomes effective exactly if a later rule edit regenerates the slot, preserving the user's remove intent across detach/re-attach cycles. Then `touchUpdatedAt(parent)`.
  - **`revert` (explicit opt-in, sent only by the new "Revert to series schedule" UI):** soft-delete the child AND **re-materialize a `TaskOccurrenceException`** carrying the child's `completedAt` (and, for backfill-migrated children, the recorded prior skip state) in the same transaction (rev, was issue 14): §4.2 step 4 hard-deleted the pre-override exception (exceptions have no tombstone), so a bare revert would silently un-complete an occurrence the user completed weeks ago and corrupt completion reporting (`task.entity.ts:87-92`). Revert restores the pre-override exception state, not a blank slate. Then `touchUpdatedAt(parent)`.
  - **Both modes `touchUpdatedAt(parent)` (rev, was issue 20):** the child tombstone alone deletes the local child row on other devices but invalidates no `WindowSyncMeta` — the regenerated (revert) or skipped (remove) slot would render wrong/empty until an unbounded TTL+trigger refetch. The parent touch rides the delta and §5.5 rule 2 invalidates the affected months.
- `POST /tasks/:parentId/skip` on a slot that has a live override ⇒ `409 OCCURRENCE_OVERRIDDEN` (client should call `DELETE child` instead — plain default mode).
- Optional (P2): `GET /tasks/:parentId/overrides` → `TaskDTO[]` for a future "manage exceptions" UI.

### 4.4 List / window / counts semantics

- `GET /tasks` (`task.controller.ts:59`): returns generated occurrences **minus suppressed slots**, plus override children as occurrences with `taskId = childId`, `parentTaskId = parent`, `originalStart = child.originalStartAt`, `isRecurring = false`, `isDetached = child.detachedAt != null`. Suppression query: `SELECT id, "originalStartAt" FROM task WHERE "parentTaskId" = ANY(anchorIds) AND "originalStartAt" >= :from AND "originalStartAt" < :to AND "deletedAt" IS NULL` — keyed on `originalStartAt`, NOT `startAt`, because a child moved to another month must still suppress its original slot in the original month's window (covered by `UQ_task_override_slot`). `anchorIds` includes **group-inherited anchors** (rev, was issue 16 tail). Plus the one-off wrap suppression for former parents (§1 step 4).
- `GET /tasks/daily-counts` (`task.service.ts:508-534`), the assistant's `ScheduleReaderService` (`schedule-reader.service.ts:32`), and the daily-report generator (`report-generator.service.ts:78`) all reuse `findOccurrencesInRange` ⇒ they inherit suppression + merge for free.
- Conflict checks: **`findOverlapping` (recurring branch `task.service.ts:1402-1469`) receives the suppression map in Phase B1, same deploy as the read-path suppression** (rev, was issue 10 — shipping the override endpoint with unsuppressed conflict expansion makes the assistant hold-confirm on a phantom conflict at the vacated slot while the calendar UI shows it free). The edit/series preview variants (`findRecurringSeriesConflicts`, `findRecurringEditConflicts`, `previewSeriesOccurrences` at `recurrence-rule.service.ts:632-665`) follow in Phase B3.
- `includeCompleted=false` default (`list-tasks.query.ts:38-47`) applies to children like any task: a completed override vanishes from the window on the next revalidate — consistent with today's ephemeral-completed behavior; not a regression, but note it.

### 4.5 Completion on an overridden slot — server-side redirect (rev, was issues 2/13, critical)

`setOccurrenceCompleted` (`task.service.ts:575-604`) is deliberately lenient today; its docblock premise ("a completion on a phantom coordinate is harmless and never surfaces in a read") is **falsified** by suppression: the coordinate of an overridden slot is a real, visible instance whose truth lives on the child. Without a fix, a device holding a TTL-fresh cached generated row (5-min `WindowSyncMeta` TTL, `CalendarStore.swift:44`) completes via `PATCH /tasks/{parentId}/completion` + `originalStart` → an exception `{completedAt}` is written at a suppressed slot → the completion never surfaces (child `completedAt` stays null), the exception is permanently orphaned, and if the child is later revert-deleted the stale exception zombie-completes the regenerated slot.

**Fix:** in the recurring branch of `setOccurrenceCompleted`, first check for a live child at `(taskId, originalStart)` (`UQ_task_override_slot` makes this a point lookup). If found, **redirect the write to the child's master `completedAt`** and return that value. Old clients need zero changes and get correct behavior (a 409 like skip would be unactionable for a client that doesn't know the error). The lookup runs inside the same transaction pattern as §4.2 step 0 (parent `FOR UPDATE`) so it cannot interleave with a concurrent override-create's exception absorption. Update the docblock — the leniency argument no longer holds unqualified.

## 5. iOS changes (deviation: expansion stays server-side)

The prompt asked for an "expansion algorithm change on iOS". **Deviation, justified:** the client never expands RRULE — expansion is 100% server-side and the client caches pre-expanded occurrences (`CalendarStore.swift:517-519`). The expand→suppress→merge algorithm therefore lands in `findOccurrencesInRange` (§4.4), and iOS receives an already-correct occurrence list. This keeps the single-expander invariant (assistant, reports, conflicts, counts, and iOS all see the same truth) and avoids duplicating DST-correct RRULE math in Swift.

### 5.1 DTO / model / mapping

- `cue/Networking/APIModels.swift`: `TaskDTO` += `parentTaskId: String?`, `originalStartAt: String?`, `detachedAt: String?`, `recurrenceUpdatedAt: String?`; `OccurrenceDTO` (:258-302) += `parentTaskId: String?`, `isDetached: Bool?`.
- `cue/Models/TaskItem.swift`: += `parentSeriesId: String?`, `isDetached: Bool = false`. `occurrenceKey` unchanged — for a child row `seriesId` is the **child's own task id** (server sends `taskId = childId`), so keys stay unique and prune/upsert (`CalendarStore.swift:154-165`) work untouched. SwiftData schema change ⇒ rides the existing destroy-and-recreate-on-mismatch path (`cueApp.swift:26-60`); cache is rebuildable, acceptable.
- `cue/Models/TaskItem+Mapping.swift`: map the new fields in both `upsert(from: OccurrenceDTO)` (:52-91) and `upsert(from: TaskDTO)` (:21-46).
- `cue/Features/Calendar/UIKit/OccurrenceVM.swift` and `cue/Features/Calendar/ScheduleEvent.swift`: carry `parentSeriesId`/`isDetached` for rendering + detail navigation. `id` stays `occurrenceKey` — children get NEW keys `childId#iso` while the suppressed generated key `parentId#iso` disappears in the same window resync commit; the snapshot diff renders remove+insert, which is semantically correct.

### 5.2 Completion / skip — zero changes needed (verify, don't rewrite)

`CalendarStore.toggleCompletion` (`CalendarStore.swift:783-833`) branches on `isRecurring`: recurring ⇒ send `originalStart`; else ⇒ omit and PATCH `seriesId`. Child rows arrive with `isRecurring == false` and `seriesId == childId` ⇒ the existing code already PATCHes the child's own completion correctly, optimistic toggle + `inFlightCompletions` shielding included. The stale-cache case (device still shows the generated row after another device overrode the slot) is covered server-side by the §4.5 redirect. Skip button must be **hidden** for child rows (5.4) — server would 409 anyway.

### 5.3 Edit flow — the decorative scope becomes load-bearing

- `cue/Features/Calendar/TaskDetail/TaskEditScreen.swift`:
  - `performSave` (:614-647): replace the "both scopes PATCH the whole series" fallback (:632-635) — scope `.this` now calls `POST /tasks/{event.seriesId}/occurrences/override` with `originalStart = event.originalStart` serialized via the `isoFractional` pattern (`CalendarStore.swift:79-87`) and a patch built from the **dirty fields only** (tri-state `FieldUpdate` machinery :649-662 reused). Scope `.all` unchanged (PATCH series).
  - Default scope: change from `.all` to `.this` for recurring tasks (Apple Calendar convention). Keep the segmented card (:252-282). *Deviation from current code, flagged for user sign-off.*
  - **(rev, was issue 9) Stale-cache failure handling:** the `.this` path can now 400 when the rendered occurrence was rekeyed by a concurrent series edit (cache TTL 5 min; delta is foreground+tab-gated). Give the server error a stable code (`OCCURRENCE_NOT_GENERATED`); on receiving it, the client runs `invalidateAndResync(around: event.occurrenceStart)` and surfaces "This series changed — review and try again" instead of a generic failure. Do NOT silently fall back to `.all` (destructive scope escalation without consent).
  - When the edited event **is itself a child** (`event.parentSeriesId != nil`): hide the scope card entirely; plain PATCH to the child id. Optionally a tertiary "Edit the whole series" link navigating to the parent.
- `cue/Features/Calendar/CalendarStore.swift`: new methods `overrideOccurrence(seriesId:originalStart:patch:)` → POST, then `invalidateAndResync(around:)` (:659-678) for BOTH the original month and (if moved) the new `startAt` month; `deleteOverride(childId:mode:)`.

### 5.5 Delta handling widening (`CalendarStore.applyDelta`, :529-578) — (rev, was issues 6/19/28)

Current case (b) invalidates month memos overlapping `[createdAt, updatedAt+1s]` (:554-561,584-608). Revised rules:

1. **Rule-change widening, keyed on `recurrenceUpdatedAt` — NOT on `dto.recurrence != nil`.** The naive `recurrence != nil` trigger both over-fires (verified: EVERY per-occurrence completion/skip funnels through `upsertOverride` → `touchUpdatedAt(parent)` in both branches of `task-occurrence-exception.service.ts` — the recurring parent then rides the delta after routine checkbox taps, and the widening would wipe all month memos calendar-wide on every completion from another device) and under-fires (a parent recurring purely via GROUP config has `recurrence: null` on the wire, so a group rule change — which moves every generated occurrence — never triggers it). New rule: for each delta `tasks[]` entry, if `dto.recurrenceUpdatedAt != nil && dto.recurrenceUpdatedAt > since` (the `since` the client sent), invalidate **ALL** month memos for that calendar. Stateless comparison; no local bookkeeping.
2. **Any changed task** ⇒ additionally invalidate the months of the task's **existing local rows** (`FetchDescriptor` on `seriesId == dto.id`, collect `occurrenceStart` months) plus `month(dto.startAt)`. This catches a child (or one-off) moved across months and, for a touched parent, covers the months of its cached occurrences.

`deleted[]` handling (:544-551) needs no change: child tombstones arrive with the child's own id and "delete all rows of that series" deletes exactly the one child row.

Server-side counterpart (rev, was issues 6/19): on group `recurrenceConfig` change AND on group delete, the server `touchUpdatedAt` + bumps `recurrenceUpdatedAt` on **every member anchor task** (bounded set, indexed by `groupId`) — the parents then ride the delta and rule 1 fires, closing the "group rule changed but only flipped children were reported" hole entirely (a childless member series previously produced ZERO delta entries).

## 6. Lifecycle policies

### 6.1 Parent rule change → **keep-as-detached** (recommended)

**Trigger set (rev, was issues 4/16/27) — any mutation of the effective-rule input set:**

| Trigger | Path |
|---|---|
| own `recurrenceConfig` replace/clear | `TaskService.update` (`task.service.ts:718-812`) |
| `startAt`, `timezone` | same |
| **`isAllDay` flip** (rev) | same — all-day occurrences are date-anchored (`recurrence-rule.service.ts:477-496`); the flip rekeys generated UTC instants exactly like a startAt change |
| **`groupId` change** (rev) | same, `nextGroupId` diff at `task.service.ts:753-802` — for a parent with no own config, moving into/out of/between groups swaps the ENTIRE effective rule (task-wins resolver, `effective-settings.ts:31-40`); sweep when either old or new group carries a rule |
| `endSeriesAt` truncation | `task.service.ts:964-993` — but see §6.3: children past the cut are DELETED, not detached |
| `splitSeries` | `task.service.ts:847-933` |
| group `recurrenceConfig` change | `TaskGroupService.update` |
| **group deletion** (rev) | `TaskGroupService.remove` (`task-group.service.ts:236-240`) — verified HARD delete with FK SET NULL on members and no `updatedAt` bump anywhere; a parent recurring purely by inheritance instantly stops recurring. Run the sweep BEFORE the hard delete, while `task.groupId` still resolves; detach children of inheritance-recurring members; `touchUpdatedAt` + bump `recurrenceUpdatedAt` on each affected parent so the delta carries the change |

Sweep (same transaction as the mutation; the transaction takes the parent `FOR UPDATE` lock per §4.2 step 0 to serialize against concurrent override creation):

```
for each live child of the affected series:
  generated = effective-config membership of child.originalStartAt under NEW effective rule
  if !generated and child.detachedAt == null → child.detachedAt = now; save()   // bumps updatedAt ⇒ delta
  if  generated and child.detachedAt != null → child.detachedAt = null; save()  // re-attach on rule revert
```

- Rationale for keep-as-detached over delete (rule EDITS only): the override embodies user edits — silently destroying it on a rule tweak is data loss; iCalendar clients (Google/Apple) keep modified instances too. Over prompt: no interactive-prompt infrastructure exists in the REST path or the assistant tool loop (held-confirm is scoped to conflicts, ADR 0024), and the decision is reversible.
- Detached children stop suppressing anything real, keep rendering at their own `startAt`, and remain linked for provenance.
- Rule-clear special case (rev, was issue 30): when `recurrenceConfig` is cleared (tri-state null, `task.service.ts:1499-1513`) the parent degrades to a one-off wrapped at its own `startAt`. A live child at the anchor slot (`originalStartAt == parent.startAt` — the common "edited the visible instance" case) would then render alongside the parent one-off as a duplicate. Policy: the anchor-slot child stays **attached** (its instant still surfaces via the one-off wrap) and the wrap suppression of §1 step 4 hides the parent's own occurrence — the user's edited instance wins, no duplicate, no data loss. All other children detach normally.
- Note the sibling landmine this fixes only for overrides: exception rows (skip/completion) at rekeyed instants remain orphaned exactly as today (Landmine A). Out of scope; do not regress, do not fix silently.

### 6.2 Parent deletion → **cascade soft-delete** (recommended)

`TaskService.remove` (`task.service.ts:940-946`) extends to: soft-delete parent, then soft-delete each **live child individually via `.save()`** in the same `@Transactional` block — each child needs its own `deletedAt` + `updatedAt` bump so `GET /tasks/changes` emits **per-child tombstones** (the client deletes local rows by the row's own `seriesId`, `CalendarStore.swift:544-551`, so a parent-only tombstone would strand child rows).

Rationale for cascade over orphan-to-standalone: (a) "Delete series" in the iOS UI already promises whole-series removal and the client already purges every local row of the series (`TaskDetailScreen.swift:400-424`, `CalendarStore.swift:837-849`); (b) iCalendar semantics: deleting the series deletes modified instances too; (c) the user who wants to keep one instance has the explicit tool — detach/keep. The FK's ON DELETE SET NULL remains only as a hard-delete safety net (§3.1), now actually reachable with the one-directional CHECK (§3.2). If the product intent is instead "keep my edited instances," flip the policy to detach-instead-of-delete — the schema supports both; open question.

**(rev)** `TaskService.remove` is also where the child-DELETE semantics of §4.3 live (when the target itself IS a child): mode-less remove ⇒ child soft-delete + unconditional skip exception + parent touch. This single choke point is what makes the assistant's `handleDeleteTask` (which calls `remove` directly) and old iOS builds safe without touching them.

### 6.3 `splitSeries` / `endSeriesAt` (assistant-only paths)

- `splitSeries` (`task.service.ts:847-933`): children with `originalStartAt >= splitPoint` are **reparented** to the new series row (`parentTaskId = newId`) in the same transaction — symmetric with the existing exception-copy (:930, 1628-1652). Run the detach sweep on both halves (cheap, catches COUNT edge rounding).
- **`endSeriesAt` (rev, was issue 18): cascade soft-delete, not detach.** "Delete this and following" is a DELETION verb: live children with `originalStartAt >= originalStart` are soft-deleted (per-row `.save()`, tombstones) in the same transaction, matching (a) user intent — a moved/edited July 20 instance must not survive "delete everything from July 10", (b) iCalendar behavior, and (c) the collapse branch: `endSeriesAt` at the FIRST occurrence already collapses to `remove()` (verified `task.service.ts:972-981`), which cascades under §6.2 — detaching from occurrence 2 onward while cascading from occurrence 1 would treat identical children oppositely. Keep-as-detached is reserved for rule EDITS (§6.1).
- Pre-existing bugs adjacent to this code, flag do-not-repeat: split loses per-task reminders (:910-926) and `cloneConfigWithOverrides` can't overlay `bySetPos/monthlyAnchor` (:1722-1745).

## 7. Interplay

### 7.1 Per-occurrence completion records
- Non-overridden occurrences: unchanged — exception rows, `PATCH /tasks/:id/completion` + `originalStart` (`task.service.ts:581-604`). The hot optimistic-toggle path (`CalendarStore.swift:783-833`) is untouched. Deliberate decision NOT to materialize a task per checkbox tap: row churn, delta noise, id churn in diffable snapshots, in-flight-shield rewrite — for zero user value.
- Overridden occurrences: completion lives on the child's master `completedAt` (`task.entity.ts:87-92`). At override creation/upsert, an existing exception `completedAt` is absorbed onto the child and the exception deleted (§4.2 step 4); a completion PATCH addressed to the parent at an overridden slot is **redirected to the child server-side** (§4.5) — one source of truth per slot even with stale-cache clients.

### 7.2 Reminders
Children get real `NotificationRule` rows (`notification-rule.entity.ts:26-63`) copied from the parent at creation and thereafter fully independent (edit/clear via the existing full-replace PATCH semantics, `task.service.ts:777-781`). Delivery remains unbuilt (ScheduledNotification skeleton) — this design makes per-occurrence reminders *representable* now; the future delivery worker (`docs/specs/notification-delivery.md`) must additionally suppress fire times for overridden slots — note that in the worker's spec when it lands. Known delta caveat carries over: reminder-only edits still don't bump `task.updatedAt` (`task.service.ts:784-798`) — applies equally to children; out of scope.

### 7.3 Telegram assistant — (rev, was issue 21, critical correction)
The two dispatcher sites previously slated for rewiring are NOT both edit paths. Verified in the working tree:
- The `'this'`-scope **EDIT** handler (`scope === 'this'` branch calling `buildOccurrenceOverrideChanges` → `taskService.applyOccurrenceOverride`, around `tool-dispatcher.service.ts:974-987`) — **this is the ONLY site rewired** to the new `createOrUpdateOverride` service method. Its pre-read of the existing exception (`findOccurrenceException`, used by the move-conflict gate to preserve a prior length change) maps onto §4.2 step 4's absorption.
- The `'this'`-scope **DELETE** handler inside `handleDeleteTask` (`if (isRecurringInstance && parsed.editScope === 'this') { applyOccurrenceOverride(..., { isSkipped: true }) }`) — **keeps skip semantics.** Rewiring it as originally written would turn "delete just Friday's occurrence" into CREATING an override task and replying 'Removed this occurrence.' — a false-success write. Add one branch: if a live child exists at the slot, call `remove(childId)` (which under §4.3 soft-deletes the child + writes the skip), mirroring the 409 guard on `POST /tasks/:id/skip`.
- The whole-task delete at the bottom of `handleDeleteTask` calls `taskService.remove(...)` verbatim — safe without changes because the child-aware remove semantics live in `TaskService.remove` (§6.2).

Tool JSON schemas unchanged. Targeting works without schema changes because `ScheduleReaderService` consumes `findOccurrencesInRange` (:32): override children surface with their own `taskId`, so subsequent assistant completions/edits on them route through `setCompleted`/`update` as ordinary tasks (dispatcher :1466-1473, :1069). Conflict preview: `previewSeriesOccurrences` receives the suppression map in Phase B3; `findOverlapping` gets it in B1 (§4.4). The assistant's recurrence schema still doesn't expose `bySetPos/monthlyAnchor` (`shared-json-schema.ts:10-55`) — unaffected.

### 7.4 Delta/sync layer (sibling design)
- Children sync as normal tasks: creates/edits via `tasks[]` (`updatedAt > since`, `task.service.ts:410-417`), deletions via `deleted[]` tombstones (`.withDeleted()`, :422-429) — **zero server delta changes** beyond the new TaskDTO fields. `TaskDTO` in the delta omits reminders (controller :137-139) — unchanged.
- Parent rule change: `.save()` bumps `updatedAt` AND `recurrenceUpdatedAt` ⇒ delta reports it ⇒ §5.5 rule 1 drops all month memos ⇒ every window re-pulls server-side re-expansion on next touch. Group-side changes reach the delta via the member-parent touches (§5.5 tail). Override create/absorb and child delete (both modes) also `touchUpdatedAt(parent)` so affected months invalidate on all clients.
- The cheap "did anything change" signal from the sibling design (`max(task.updatedAt) withDeleted` per calendar) automatically covers children.

## 9. Migration & backward compatibility

1. **Schema migration** (additive, §3.2; id `1783800000000` — `1783700000000` is taken) — no downtime, no rewrite of existing rows.
2. **Data backfill — a standalone Nest script, NOT a TypeORM migration (rev, was issue 25).** The conversion needs the recurrence engine (luxon expansion for membership checks), parent-snapshot resolution, and NotificationRule copying — service-layer semantics unavailable inside a migration class (they are TS classes with a bare `queryRunner`, no DI; see any file in `src/migrations/`). Ship a one-off script that bootstraps a Nest application context (`NestFactory.createApplicationContext`) and runs post-deploy on the EC2 box (same channel as `deploy.sh`). Policy per `task_occurrence_exception` row with `overrideStartAt IS NOT NULL OR overrideTitle IS NOT NULL OR overrideEndAt IS NOT NULL` (assistant-created only; REST never wrote these):
   a. **`isSkipped = true` rows are NOT converted** (rev, was issue 17): the exception upsert is last-writer-wins on the unique key, so a row can carry both a skip and override fields; the skip wins — the slot is hidden today and must stay hidden. Strip the override fields, keep the skip.
   b. **Membership check under the EFFECTIVE rule** (own ?? group). Generated ⇒ convert to an attached child per §4.2 semantics — including `endAt = overrideEndAt ?? (start + parentDuration)` (rev, was issue 7: dropping `overrideEndAt` would silently shrink every previously-resized occurrence fleet-wide) — absorb `completedAt`, delete the exception, touch parent.
   c. **Orphaned rows (membership fails — Landmine A residue) are NOT converted** (rev, was issues 17/25): they are invisible today; materializing them would make weeks-old ghost events reappear on calendars after the deploy — a behavior change, not a preservation. Leave the rows in place (inert, as today), log their count/ids, and archive them (JSON dump) before the follow-up column-drop migration so nothing is silently destroyed.
   The script is idempotent (skips slots that already have a live child) and wraps each row in its own transaction.
3. **Wire compat**: all DTO additions nullable; Swift Codable and old clients ignore them. `ChangesDTO` unchanged. No endpoint removed; `PATCH /tasks/:id/completion` and `POST /tasks/:id/skip` contracts unchanged (completion gains the invisible server-side redirect §4.5).
4. **Old-client windows**: after a new client (or the assistant) creates an override, an old client's next window revalidate prunes-then-upserts (`CalendarStore.swift:154-165`) — the suppressed generated row disappears and the child appears as a plain task. Correct-if-unlabeled. Old-client DELETE of a child is safe (default `remove`, §4.3).
5. **SwiftData**: new `TaskItem` fields ride the existing destroy-and-recreate-on-schema-mismatch container path (`cueApp.swift:26-60`); cache rebuilds from server.
6. **Follow-up migration (one release later)**: drop `overrideStartAt/overrideEndAt/overrideTitle` from `task_occurrence_exception` and remove their application in `buildOccurrence` (`recurrence-rule.service.ts:448-474`), after the archive of §9.2c.

## 13. Rejected / corrected review points

All 30 findings were verified against the working tree; none were rejected outright. Corrections and partial rebuttals:

1. **Issue 25(1), "cannot run inside a SQL migration — not implementable"** — overstated. cue-api migrations are ordinary TypeScript classes implementing `MigrationInterface` (verified, e.g. `src/migrations/1783700000000-seed-persona-presets.ts`), so arbitrary TS *can* run there; what they lack is Nest DI, which the luxon expansion engine and reminder-copy logic need. The recommendation (standalone backfill script) is adopted anyway because it is the right mechanism, not because a migration is literally incapable.
2. **Issue 3, "any future data-repair that nulls parentTaskId … loses the RECURRENCE-ID"** — minor overstatement even against the original schema: a single UPDATE can set both columns atomically. Moot under the adopted one-directional CHECK, where nulling `parentTaskId` alone is legal and `originalStartAt` is retained.
3. **Issue 9's fallback option "offer the `.all` scope"** — rejected in favor of resync-and-retry: silently escalating a failed single-occurrence edit to a whole-series PATCH is a destructive scope change without consent.
4. **Issue 17 vs 25 orphan-policy conflict** (issue 25 suggests converting orphans as `detachedAt`-set children; issue 17 argues not to convert at all) — sided with issue 17: orphaned legacy overrides are invisible today, and materializing them resurrects ghost events. Archive-before-drop preserves the data without the behavior change (listed as open question 3).
5. **Issue 30's "absorb the child back into the parent" option** — rejected as a mutation of the parent beyond the user's request; the one-off wrap suppression (§1 step 4) resolves the duplicate with no data movement.
6. **Issue 2's alternative "409 like skip"** — rejected in favor of its own primary suggestion (redirect): a stale old client cannot react to an error code it does not know; the redirect keeps it correct with zero client changes.
7. **Issue 19's suggestion of an `isRecurring`/`effectiveRecurrence` boolean on the delta DTO** — superseded by issue 28's `recurrenceUpdatedAt` (adopted): a boolean flag would re-introduce the over-fire (every completion parent-touch of a recurring series would wipe all month memos), which issue 28 itself demonstrates is a real path (`upsertOverride` → `touchUpdatedAt` in both branches, verified in `task-occurrence-exception.service.ts`).
